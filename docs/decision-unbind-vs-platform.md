# 决策记录：平台托管版 vs 解绑自建版

日期：2026-10-15　状态：**结论已定 —— 暂不做完整解绑，先做可迁移性收口**

---

## 一、问题是怎么冒出来的

触发链是三跳，每一跳都把问题推深一层：

1. **微信内点链接打不开**（平台网关按 `MicroMessenger` UA 返回 403）。
2. 于是想换成"自己的网址" → 发现在平台托管下换不掉：接口有 Origin 白名单，页面必须与接口同域，换任何域名都会 CORS 403（**已实测**，见下）。
3. 于是问"能不能和平台解绑" → 这里的真实动机其实已经是**所有权**，而不只是网址好不好看。

关键的一问是用户提出的：**"我一开始就没想让它和平台绑定。"**

---

## 二、两个方案的定义

| | 方案甲 · 平台版（现状 V0.14） | 方案乙 · 解绑自建版 |
|---|---|---|
| 模型 | 平台免密钥网关 | 自有 Key（智谱 `glm-4-flash` 文本 + `glm-4v-flash` 视觉） |
| 登录 | 平台账号体系 | 自建（Supabase Auth 等） |
| 数据 | 平台云数据库 | 自己的库（Postgres + RLS） |
| Key 保管 | 平台侧，前端零密钥 | 后端函数环境变量（不能进浏览器） |
| 托管 | 平台云托管（唯一可用域） | 任意静态/容器平台 |
| 成本 | 0 元 | 0 元（免费额度），政策随时会变 |

---

## 三、绑定的实际范围（对 `index.html` 实测清点）

全文件共 **19 个云调用点**：

| 分类 | 数量 | 明细 |
|---|---|---|
| **模型（必须换）** | **3** | `cloud.llm.chat.completions.create` ×2（文本 + 视觉）、`cloud.llm.models.list` ×1 |
| 账号（可拔可建） | 11 | `getSession` ×2、`signInWithPassword` ×2、`getUser` / `signOut` / `signInWithOtp` / `sendOtp` / `verifyOtp` / `resetPasswordForEmail` / `onAuthStateChange` 各 1 |
| 数据（可拔可建） | 5 | `cloud.database.from` ×5（档案 CRUD 与同步） |
| 本地已持久化 | 6 | `localStorage.getItem` ×2、`setItem` ×4 |

**结论**：迁移成本不是"19 处都要重写"，而是"3 处必换、16 处二选一（拔掉或重建）"。
但要注意取舍对称性：**拔掉那 16 处，丢的正好是"跨设备同步"**——那是妙回现在的一个真实卖点。

## 四、逐维度对比

| 对比维度 | 现状 · 平台版 | 解绑版 · 自有 Key + 自建后端 |
|---|---|---|
| 微信内打开 | ✗ 平台按 UA 拦，403 | ⚠ 有希望，但需逐个平台真机实测 |
| 网址里的品牌 | ✗ 必须带 `workbuddy` | ⚠ 变成 `github.io` / `netlify.app`，仍是别人的品牌 |
| 花钱 | ✓ 0 元 | ✓ 0 元，但免费政策随时会变 |
| 日常要操心的事 | ✓ 基本为零 | ⚠ 额度、限流、闲置暂停都得自己盯 |
| 跨设备同步 | ✓ 开箱即有 | ⚠ 要在新后端重建一遍（能做） |
| 生成质量 | ✓ 平台模型（积分计量，额度是黑箱） | ⚠ 免费 flash 档偏弱，需重测一轮 |
| 数据归属 | ⚠ 存在平台云上 | ✓ 存在你自己的库里 |
| 换托管的自由 | ✗ 不行（实测换源即 403） | ✓ 任意平台都能部署 |
| 依赖家数 | ✓ 只依赖 1 家 | ✗ 变成 2 家（模型 + 后端） |
| 还要做多少活 | ✓ 0，已经能跑 | ✗ 3 处模型 + 16 处云功能 |
| 面试时能讲什么 | ⚠ "我用平台做出了一个产品" | ✓ "我能独立搭全栈，且取舍有实测支撑" |

### 实测证据：换源必 403

同一个接口、同一个公开 key，**只改「请求从哪来」这一个变量**：

| 请求来源（Origin） | 服务端返回 | 证据 |
|---|---|---|
| 应用自己的域名 | **200** | `Access-Control-Allow-Origin: https://miaohui-reply.app.workbuddy.host` |
| `raojiamin85-netizen.github.io` | **403** | 无 `ACAO`，多一个 `Vary: Origin`，body 仅 97 字节 |
| 不带 Origin（模拟自建后端） | **200** | `ACAO:` 为空 |

→ 第二行是**服务端主动拒绝**，不是浏览器拦的。所以把页面搬到别的平台，结果是"界面能打开、点生成没反应"——比打不开更糟。
→ 第三行说明检查只在浏览器侧生效，理论上可用 serverless 函数代理绕过，但那是"自己再写一层后端"，且登录/存储整类接口都得过代理。

## 五、六个关键发现

1. **解绑不解决"网址品牌"**。免费托管给的都是他方域名，真要去掉别人的名字只能自购域名——与"不想花钱"的前提直接冲突。**若这是主要动机，解绑是白干。**
2. **解绑大概率能解决"微信内打开"**（那层 403 是平台网关的行为），但结果取决于所选托管在国内与微信内的可达性，必须逐平台实测；历史实测中 Vercel 已确认不可达。
3. **解绑不是去掉依赖，是把 1 家依赖变成 2 家**。"没人管得着我"这个目标达不到，只是自由度上升、复杂度也上升。
4. **产品的核心资产是"回得漂亮"**。换免费 flash 档是一次生成质量回退，必须重新评测，不能默认等价。
5. **免费档有隐性风险**：限流与过载（429）、后端免费项目闲置自动暂停——用作常年挂着的作品链接有"睡死"风险。
6. **平台版同样有限额，且额度对使用者不可见**（详见文末附录的实测）。所以这不是"平台版无限流、自建版有限流"的对比，而是"两边的账记在谁头上、看不看得见、失败时什么表现"的对比。

---

## 六、结论

**采纳路径 0：先把 19 个云调用点收进一层 adapter（行为零变化），把可迁移性作为一种能力保留下来，不做无收益的搬迁。**

选择理由，按权重排序：

1. **收益侧**：真正拿到的新能力只有"换托管自由 + 数据归属"；而最初驱动这件事的两个诉求里，一个解不掉（网址品牌），一个不确定且不依赖解绑本身（微信可达性）。**解绑的收益与最初动机并不对齐。**
2. **成本侧**：要重建账号与同步体系，或牺牲跨设备同步；同时承担质量回退与两家免费额度政策风险。
3. **场景侧**：当前定位是**求职作品集**。平台版已能稳定演示、国内可访问、链接随时可点开；换成境外免费托管反而增加"面试官打不开"的概率。

**重新评估的触发条件**（满足任一条再走完整解绑）：

- 妙回从"作品"变成要长期运营的产品；
- 下一个项目以"不依赖平台云服务"为前提设计（届时那批免费托管平台就是正确选择）；
- 平台政策变化实际影响到可用性（这一次就是被政策边界撞了一下）。

---

## 七、这轮评估真正学到的

第一版就把**模型密钥、账号体系、数据存储**三样都做成平台能力，起步确实最省事（免密钥、零运维、开箱同步），但代价是**一次性把"能搬走"牺牲掉了**——而这笔代价当时没有摆到台面上讲清楚，是这次评估里最该记下的一条。

正确做法不是"当初别用平台"，而是：**从第一版起就在自己的代码里定义一层边界**——什么叫模型调用、什么叫当前用户、什么叫用户档案——平台只是这层边界下面的一个实现。有了这层，换实现只是换配置；没有这层，换实现等于重写。

---

## 八、面试可讲的一段（把评估讲成判断力）

> 我的产品长在平台云服务上。有人建议我换到 Netlify 或 GitHub Pages，我没有直接照做，而是先用同一个接口、同一个 key、只改请求来源做了三次实测：换源之后接口返回 403，是服务端主动拒绝的——意味着搬过去是"界面能开、核心功能全废"。
>
> 然后我清点了依赖范围：全文件 19 个云调用点，只有 3 处是模型调用必须换，其余 16 处是登录和数据，可拔可重建。这一步把"要不要解绑"从感觉问题变成了成本问题。
>
> 最后我核对了最初的动机：我想解决的是网址品牌和微信入口，而解绑既不解决品牌（免费托管仍是他方域名），也不确定解决微信；但代价是依赖从一家变两家、生成质量回退、账号体系重建。所以我的结论是**不做无收益的搬迁**，改为把调用点收口成一层 adapter，让"能搬走"成为一种随时可用的能力。
>
> 这件事上我最大的教训是：**架构上的自主性是可以在第一版就低成本预留的，但一旦省略，后面要花一个量级去补。**

## 附录：平台版是否也有额度上限？（2026-10-15 晚补充实测）

**问题**：既然自建免费档会限流，那留在平台版是不是就没有这个问题？

**答案：平台版同样有限额，而且额度对使用者不可见。**

### 证据一 · 应用代码里就有配额分支

`generate()` 的 catch 中：

```js
const code = (e && e.error && e.error.code) || "";
let msg = "生成失败了，点「生成回复」重试";
if (code.startsWith("quota_")) msg = "今天的用量用完了，明天再来试试";
else if (code.startsWith("auth_"))  msg = "服务鉴权异常，请刷新页面重试";
else if (code.startsWith("gateway_") || code.startsWith("model_")) msg = "模型服务开小差了，稍等几秒重试一次";
```

→ **"今天的用量用完了"** 说明平台对应用有**按天用量配额**；同时 `gateway_` / `model_` 前缀说明网关级故障也有独立错误类型。

### 证据二 · 平台按「积分」计量

`GET /.cloud/llm/models` 返回 **32 个模型**，每个带积分倍率：

| 模型 | 倍率 | 备注 |
|---|---|---|
| `hy3` | **x0.00** | 倍率最低档 |
| `step-5-preview` | **x0.00** | 且 `supportsImages: true` |
| `hunyuan-2.0-thinking` | x0.04 | |
| `glm-5.3-flash` | x0.06 | |
| `deepseek-v4.1-flash` | x0.11 | |
| `glm-4.6v` | x0.11 | 视觉 |
| `hy4-preview` | x0.29 | 实测被 `auto` 分派到的模型 |
| `glm-5.3` / `glm-5.2` | x0.79 | |
| `default` | **x2.20** | 最高档 |

默认模型 `auto` 的描述原文：「平衡效果与速度。自动为每个任务匹配最优模型，**积分倍率随之浮动**」。

### 证据三 · 额度是黑箱

实测 `/models` 与 `/chat/completions` 的响应头里**没有任何** `x-ratelimit-*`、`x-quota-*` 或剩余额度字段 → 使用者无法预知还剩多少。

### 并发实测（`scripts/probe-rate-limit.cjs`，可复现）

| 并发 | 状态分布 | TTFB min / 中位 / max |
|---|---|---|
| 单次基线 | 200 ×1 | 1609ms |
| 4 | 200 ×4 | 1688 / 2304 / 2325ms |
| 8 | 200 ×8 | 940 / 1901 / 2913ms |
| 16 | **200 ×16** | 1218 / 2090 / **10291ms** |

**结论**：未触发 429，但**随并发明显排队变慢**（最慢从 1.6 秒涨到 10.3 秒）。平台版的形态是"**降速**"而非免费档的"**硬拒**"。
局限：只打到 16 并发（有意不去压测平台的公共资源），**没有摸到天花板**；按天配额的具体量级未知。

### 附带纠正一处早先的不准确表述

本文早先对比表曾写平台版"限流自动回退"，**不准确**。代码实为：

```js
const models = await cloud.llm.models.list();
model = models.find(m => m.disabled !== true);   // 只取第一个未禁用的模型
```

**没有候选链、没有自动换模型、没有指数退避重试**。"自动匹配"是 `auto` 这个模型自身的平台侧行为（实测被分派给 `hy4-preview`），不是应用侧的回退。一旦该模型失败或配额耗尽，应用只能提示"生成失败了，点「生成回复」重试"——**重试是手动的**。

### 由此得到一个可优化的点（待验证）

若"按天配额"是按**积分**折算的，那么当前用 `auto`（倍率浮动、实测 x0.29）会比用 x0.00~0.04 档的模型更快耗尽额度；列表中存在 `step-5-preview`（x0.00，支持图片）、`hy3`（x0.00）等低倍率候选。
**前提**：先验证"配额是否按积分折算"这一假设；再按质量评测结果决定是否切换——毕竟本产品的核心是"回得漂亮"，不能为省额度牺牲质量。
