# 妙回 · 产品定义文档（v1）

> 阶段 1 产出 · 2026-09-27 · 这是整个项目的"需求源头"，逐版决策与踩坑复盘的起点。

## 一句话定位

把对方发来的聊天内容贴进来，选好你想达到的效果，得到 3 条"像你自己说出来"的候选回复。

## 用户与痛点

- 目标用户：社交/职场沟通中"收到消息不知道怎么回"的普通人（第一个用户就是我自己）
- 痛点本质：**不是缺回复，是缺意图**——卡住的原因是想不清楚"我回这句话想达到什么效果"

## 核心洞察（产品的灵魂）

按"意图"组织产品，而不是按"对话场景"穷举。社交意图是有限集，场景是无限集。

## 意图清单（v1，10 个）

| # | 意图 | 典型场景 |
|---|------|---------|
| 1 | 答应并推进 | 接下任务/邀约，给出下一步 |
| 2 | 答应但争取条件 | 想接，但要缓一缓/要资源/要改时间 |
| 3 | 委婉拒绝 | 不想接，不伤关系 |
| 4 | 拖延一下 | 还没想好，先稳住对方 |
| 5 | 接住话头不冷场 | 对方发的消息不知道接什么 |
| 6 | 表达关心走心 | 朋友有事，想安慰/恭喜但不套路 |
| 7 | 道歉认错 | 承认问题，不过分卑微 |
| 8 | 催促提醒 | 要回复、要东西、要进度 |
| 9 | 幽默化解 | 活跃气氛、开玩笑接梗 |
| 10 | 砍价/谈判 | 买卖、合作条件拉扯 |

## MVP 范围

**做**：单页 Web 应用。输入聊天上下文（可贴最近几条，**也可上传聊天截图自动识别成文字**）→ 选意图 → 选对方身份（决定语气分寸）→ 可选贴 3–10 条自己的历史消息做风格校准（**可存为档案复用，登录后跨设备同步**）→ 可选补充说明 → 生成 3 条不同策略的候选回复（每条附一句"这条的思路"）→ 微调（更短/更委婉/更口语）或换一批 → 每条可标"能用/太假"形成反馈闭环 → 一键清空回下一条。

**不做**（MVP 边界，防 scope 失控）：历史聊天记录云端存储、多轮自动代聊、小程序、RAG、第三方登录与社交关系链授权。

> 注：v0.9 按用户明确要求引入了邮箱账号体系（仅用于风格档案跨设备同步），原"账号系统"这一条边界据此调整。

## 截图识别输入（v0.6 · 2026-10-14 新增）

**要解决的问题**：真实使用场景里，用户不会为了用工具而手动把聊天记录打一遍字——这层输入摩擦会把大部分人在第一步就劝退。

**设计要点**：

1. **零摩擦入口**：选图上传 / 直接 Ctrl+V 粘贴 / 拖拽到区域，三条路径任一可用；手机上就是选相册里的截图
2. **多图按序拼接**：最多 3 张（长对话常跨屏），按上传顺序拼接，保证时间顺序不乱
3. **说话人归属**：识别时让模型判断气泡左右，本人消息加「我：」、对方消息加「对方：」前缀——这一步是给下游生成用的：知道谁说了什么，回复才能衔接自然
4. **前端压缩**：上传前等比压缩到最长边 1280px 再转 JPEG(0.9)，控制 token 成本与等待时间
5. **可纠正**：识别结果直接落进输入框，是普通文本，用户可自行修改；识别失败可单张重试
6. **隐私边界**：截图仅用于当次识别，不落库、不留存；页面明示

**技术判断**：走视觉多模态直读（LLM 原生读图），不引入 OCR 专用模型。理由是截图属于"版面简单、量小、一次性"的输入，让模型直接看图并按业务规则（说话人归属、忽略状态栏）输出结构化文本，比"OCR 引擎 + 后处理规则"链路更短、更少维护成本。

## 风格档案：把"一次输入"变成"一次资产"（v0.7 · 2026-10-14 新增）

**要解决的问题**：风格样本每次都要重贴，是重复劳动。而一个人的说话风格在一定限度内是稳定的——正确的做法是**让用户输入一次、长期复用**，只在换场景（对象不同）时才切换。

**设计要点**：

1. **默认展开**：03 区块取消折叠，直接铺开。理由是这一步虽然标着"可选"，但它是效果的胜负手——藏起来等于鼓励用户跳过
2. **多档案切换**：风格样本可存为具名档案（如"对朋友""对领导""对客户"），点一下即切换；当前生效的档案高亮，一眼知道现在用的是哪套语气
3. **对方身份联动**：选了"对方是谁"之后，名字里含该身份的档案会显示为虚线建议态（仅当输入框为空时），引导切换而不是自动改——不做用户没要求的事
4. **可选择、可退出**：「本次不使用风格」一键清空本次样本，但档案保留，随时切回；档案可单个删除
5. **截图提取自己的话**：03 也支持上传截图，但提示词与 01 不同——只提取"靠右气泡（本人）"的消息，不加「我：」前缀，直接得到干净的风格样本
6. **记忆边界**：档案默认存 localStorage、不上传，同一浏览器同一设备有效；v0.9 起登录后可同步到云端、跨设备可用（见下文「账号与跨设备同步」）

**产品判断**：这一版把一个"每次都要手动喂数据"的工具，变成了"越用越懂你"的工具——用户投入的时间会沉淀成资产。这也是留存设计的起点（档案在，用户就还会回来用）。

## 一键清空：把"清空"设计成有选择性的（v0.8 · 2026-10-14 新增）

**要解决的问题**：聊完一条消息想接着回下一条时，要一个个模块手动删（上下文、补充说明、意图、身份、截图缩略图），流程被打断。

**设计要点**：

1. **清"这一条消息"，不清"你这个人的资产"**：清空范围 = 聊天上下文、补充说明、01 的截图、意图与身份选择、结果区；**保留**风格样本与全部风格档案。理由——风格是用户长期积累的资产，误清一次等于让他重新干活，而上下文重贴只是几秒钟的事
2. **清完明确告知保留了什么**：状态区显示"已清空，可以贴下一条了 · 风格样本 和 1 个风格档案 给你留着"，避免用户担心档案被删
3. **两步确认防误触**：首次点击变成"再点一下确认清空"并在 3.2 秒后自动还原，不做弹窗打扰
4. **顺手收尾**：清完自动滚回顶部并把光标落进上下文输入框，用户第一笔就能直接打字
5. **视觉还原**：结果区还原成首屏的空状态插画，页面回到"可以开始"的状态而不是空洞

**产品判断**：清空类操作的关键不是"清得干净"，而是**分清哪些是一次性输入、哪些是用户的资产**。把资产保护做对，用户才敢放心用清空。

## 账号与跨设备同步：档案从"这台设备"变成"我这个人"（v0.9 · 2026-10-14 新增）

**要解决的问题**：v0.7 的档案只存在浏览器本地（localStorage），绑定的是"域名 + 浏览器 + 设备"这个组合。关掉再打开还在，但换手机、换浏览器、清缓存就没了。用户投入建立起来的风格资产，被锁死在一台设备上。

**三条可选路线与取舍**（这是本节最值得讲的产品判断）：

| 方案 | 成本 | 隐私代价 | 结论 |
|---|---|---|---|
| 导出 / 导入文件 | 最低 | 无 | 够用但手动，换设备要倒一手 |
| 同步码（复制一段文本码） | 低 | 无 | 比文件轻，仍手动 |
| **账号 + 云端同步** | 最高 | 需引入账号体系 | **采用**——用户要求"换设备能用"，自动同步才真正解决 |

选了成本最高的那条，但用**渐进增强**把代价压到最小（见下）。

**设计要点**：

1. **本地优先，登录是增强而不是门槛**：不登录照样完整可用（档案存本机）；登录后才升级为跨设备。这样既保住了 v0.7 以来的隐私承诺，又不给临时用户设墙
2. **登录时做一次双向合并，之后两边一致**：以**档案名**为主键对齐，同名取 `updatedAt` 较新的那份，本机独有的推上云端。合并完成后本机存的就是云端那份——所以登录期间的删除不会被本机"复活"
3. **一条档案一个唯一性约束**：数据库 `UNIQUE (owner_id, name)`，同名档案天然只可能有一条，避免重复堆叠
4. **写入用「先改后增」而不是盲目插入**：先带 `name` 条件 UPDATE，若影响 0 行再 INSERT。这样既符合 RLS 语义（改不到的行说明不属于自己），也不会因重复插入报唯一键冲突
5. **未登录时云端表对它完全不可见**：只读返回 0 行、写入被拒（`permission denied`）。实测验证过——隐私边界不是靠前端不调用来保证的，是靠数据库授权和行级策略守住的
6. **失败不阻塞**：云端同步失败时，档案依旧写在本机，提示"下次登录会自动补上"。同步永远不能让用户的操作失败

**技术判断一**：用户数据的归属**不由前端声明**，而是由数据库在写入时按登录身份自动填充（`owner_id DEFAULT auth.uid()` + 行级策略 `USING (owner_id = auth.uid())`）。前端代码里没有任何一处传 `owner_id`，也拿不到别人的行——这是"把安全放在数据层，而不是放在客户端"的标准做法。

**技术判断二**：这次引入的是**邮箱认证**（密码登录 + 邮箱验证码登录 + 验证式注册 + 忘记密码），不是第三方登录。理由是目标用户是普通聊天用户，邮箱是唯一不需要额外账号体系的身份凭证，且不涉及拿到用户社交关系链这种过度授权。

## 登录态判定修复：一次「明明登录成功，界面却说不认识你」的排查（v0.10 · 2026-10-14）

**现象**：用户注册账号后，登录弹层能正常关闭，但导航栏始终显示「登录同步」，看起来像登录失败。

**排查过程（可复用的调试方法）**：
1. 先排除「密码错」：直接打一次登录接口，发现服务端对**密码错误**和**邮箱不存在**返回**完全相同的通用错误**（`INVALID_USERNAME_OR_PASSWORD`）——安全上是对的（不泄露账号是否存在），但意味着从错误文案无法区分原因，必须换证据源。
2. 再排除「接口调用写错」：读 SDK 实现，确认 `signInWithPassword({email,password})` → `/v1/signin` 的参数形状、`verifyOtp` 的注册链路（`isExistingUser` 为假时把 `password` 带去 `signUp`）都与官方文档一致，注册路径没问题。
3. 最后盯住「会话对象本身」：读 SDK 的用户映射函数，发现 **`session.user` 只暴露 `id / name / avatarUrl / isAnonymous / raw`，根本没有 `email` 字段**（带 `email` 的是 `getUser()` 走的 `/v1/user/me` 那条映射）。而导航栏的渲染判据写的是「有邮箱才算登录」——于是**登录成功也永远渲染成未登录**。

**根因**：把「展示字段」当成了「状态判据」。

**修复**：
- 登录态一律以 `session` 是否存在判断，不再依赖任何展示字段；
- 显示名走三级兜底：`getUser()` 的 email → `session.user.raw` 里的 email/username → `session.user.name/id`；
- 密码登录失败时的提示补上引导（「若没设过密码，用『忘记密码』设一个，或改用『验证码登录』」），因为**验证码登录会创建无密码账号**，这类账号用密码登录必然失败；
- 把这条坑写进自动自检脚本当回归护栏：代码里再出现「依赖 session 上的 email 字段判断登录」就会报 `REGRESSION`。

**验证**（`scripts/e2e-v010-session-render.mjs`，证据 `docs/evidence/`）：未登录基线 → 仅有 session 无任何邮箱线索（旧版必失败的用例）→ `raw.email` 有值 → `getUser()` 兜底 → 注入会话后刷新页面仍是登录态 → 退出登录回到未登录且会话被清除。7 项全过，页面零报错。

## 跨设备同步实测：从「存得上去」到「拿得回来」的闭环验证（v0.10 · 2026-10-14）

**为什么必须实测**：功能分层，风险也分层——「写入成功」只能证明 insert 路径通；真正的产品承诺是「换设备能拉回来」，它依赖的是另一条链路（select 策略 + 前端合并逻辑）。两者必须分别验，不能因为存得进去就宣布同步做完了。

**验证方法**（`scripts/e2e-cross-device.mjs`，全自动、不需要真人参与）：
1. 脚本自建一个临时邮箱（temp mail API），用它**真实走一遍注册**：发验证码 → 收件箱读取验证码 → 完成注册。这一步顺便把「新用户注册」这条链路也验了。
2. 浏览器环境 A：注册 → 存一个风格档案 → 确认提示「云端同步完成」。
3. **关闭上下文 A，开一个全新的浏览器上下文 B（本地存储为空 = 一台新设备）**，确认 A 的档案在 B 里**不存在**（证明确实没有本地残留，不是被本地数据蒙混过关）。
4. 在 B 里用邮箱 + 密码登录 → 观察档案是否被拉回、内容是否逐字一致。

**结果**：B 首次打开本机档案为空 → 登录后导航栏正确显示邮箱 → 档案 chip 出现 → 提示「已与云端对齐 · 现在换设备也能用这些档案」→ **拉回内容与原始存档逐字一致**，两侧页面均零报错。证据：`docs/evidence/app-cross-device-archive.png`、`docs/evidence/cross-device-run.log`。

**这次验证还额外证明了什么**：
- 密码登录路径可用（此前只在界面上点过，没有完整跑通过）
- 「本机为空 + 云端有」这个最容易写错的分支（漏合并、被本地空数组覆盖）经实测正确
- 测试数据用后即删，云端只保留真实用户数据，验证不污染生产

## 视觉改版：把「功能一个不少」做成可验证的工程约束（v0.12 · 2026-10-14）

**背景**：用户前后三次反馈前端"机械、丑"。前两轮都没达标，第三轮（v0.12）才通过。失败原因很具体，值得记下来：

1. **把原型的"外层画布色"当成了"页面底色"。** 喜茶原型里米色 `#EFEDE8` 是承载白纸的画布，真正的内容纸面是**纯白**。我把米色当主背景，整体就灰掉了。
2. **字号整体压小了一两号。** 原型里意图选项 19px、结果正文 21px、区块标题 25px、首屏大字 40px；我此前做到了 17/18/22/34，于是显得"糊"。
3. **擅自替换了用户认可的素材。** 用户明确说过喜欢 E1 的手绘人物涂鸦，我却换成了自创的"时钟 + 问号"。改版不是重新创作，用户认可的资产不能动。

**做法（核心判断）：换皮不换骨，而且要让"没换骨"可被机器验证。**

- `scripts/shell-v0.12.html` = 纯视觉层（HTML 骨架 + CSS + 手绘 SVG），可独立迭代
- `index.v0.10.backup.html` = 逻辑层基线，内联 JS **一行不动**
- `scripts/build-shell.cjs` = 按锚点把两者**机械拼接**成 `index.html`，并跑 6 项审计

**6 项审计**（任一不过就构建失败）：

| 审计项 | 含义 |
| --- | --- |
| id 完整性（59 个） | JS 全靠 `getElementById` 取元素，id 在功能就在 |
| JS 动态生成的 class 是否有样式（33 个） | 防"改完样式，结果卡片变成裸文本" |
| keyframes 是否都有定义（20 个） | 防动画静默失效 |
| CSS 变量是否都已声明（13 个） | 防颜色静默丢失 |
| 登录态回归护栏 | 禁止出现 `session.user.email` 判登录态（v0.10 那个 bug 的护栏） |
| 逻辑层字节一致性 | 产出里的 JS 必须与基线**逐字节相同**（仅允许版本号那一处改动） |

**设计语言**（取自喜茶官网实地抓取，`scripts/probe-heytea.mjs` → `docs/evidence/heytea-style.json`）：手绘涂鸦（SVG `feTurbulence` + `feDisplacementMap` 让**所有**线条自动手抖）、手写体大标题（站酷快乐体 + Caveat 英文）、反网格留白、几乎无 UI 控件（无卡片、无圆角、无描边按钮）、选中态用手绘马克笔下划线代替胶囊底色、分隔线是全宽浅灰手绘波浪。

**密度取舍**：品牌官网可以极稀疏，工具不能。所以骨架按 **E2（工具适配版）**走，首屏构图按 **E1**（人物左 / 标语中 / 气泡右）——两版原型都用上，而不是二选一。

**验证**：`scripts/smoke-v012.cjs` 功能冒烟 22 个用例全过（意图 / 身份 / 档案存取删载 / 两个截图入口 / 3 条候选 + 9 个操作 / 反馈展开原因 / 一键清空二次确认且保留用户资产 / 登录四 Tab / 无障碍与隐私文案），页面零未捕获异常；构建 6 项审计全绿。证据：`docs/evidence/cmp-side-by-side.png`（新旧对照）、`cmp-after-*.png`（整页 / 结果态 / 等待态 / 登录弹窗 / 手机端）、`zoom-*.png`（2× 细节）。

## 移动端故障修复：一个「点了没反应」，背后是平台差异（v0.13 · 2026-10-14）

**用户反馈**：电脑端所有功能正常，**手机端点「上传聊天截图」没反应**。

**排查（先收窄范围，再动手改）**：
1. 排除部署与缓存 —— 电脑端正常，且直连抓源码版本号一致，说明代码确实已经上线到位；
2. 排除「被遮挡」—— 导出移动端截图看，按钮可见，`.shot-row` 只是普通 flex，没有压在上面的绝对定位元素；
3. 最后落到标记本身：`<input type="file" id="shotFile" accept="image/*" multiple hidden>` —— **`hidden` 属性就等于 `display:none`**。

**根因**：移动端 WebKit（iOS Safari）以及微信等内置浏览器的 WebView，**会拒绝为「没有被渲染」的 `input[type=file]` 唤起文件选择器**。桌面 Chromium 一向宽容，所以电脑上完全正常 —— 这正是「只在手机上坏」的来源。而当时的实现是 `btnEl.onclick = () => fileEl.click()`，**完全依赖程序化点击**，平台一旦拒绝就彻底哑火。

**修复：让原生路径生效，而不是再补一次程序化 click**
- 视觉层把 input 从 `hidden` 改为 `.shot-file` 覆盖层——`position:absolute; inset:0; opacity:0; cursor:pointer`，外层用 `.shot-pick` 包住按钮；
- 覆盖层与按钮**几何完全重合**（实测都是 127×44、同一坐标），于是手指点是**直接落在 input 本身**上，走浏览器原生激活路径，不需要 JS 帮忙；iOS Safari 与微信内置浏览器都能唤起；
- 原有的 `btnEl.onclick` 保留，键盘 Enter 依然可用；
- 禁用态用 `:has()` 兜住：`.shot-pick:has(.shot-btn:disabled) .shot-file { pointer-events: none }` —— 识别中不允许绕过禁用再点。

**顺手修的移动端体验**：
- 点击热区从约 26px 提到 **44px**（Apple HIG 的最小可点尺寸）——「点了没反应」里有一部分其实是点不准；
- 缩略图上的删除 `×` 从 18px 放到 26px；
- 手机上隐藏「也可直接 Ctrl+V 粘贴」——这条提示对触屏没有意义；
- 触屏判定用 `@media (hover:none), (pointer:coarse)`，而不是宽度断点，避免「窄窗口的桌面浏览器」被误伤。

**验证**（`scripts/e2e-mobile-upload.cjs`，iPhone 13 仿真 + 真实触摸事件）：**17/17 通过**。关键用例不是「看样式对不对」，而是 `touchscreen.tap` 点在按钮上**真的抛出了 `filechooser` 事件**，随后选图 → 缩略图进列表 → 识别完成 → 4 行文字写进 01 输入框。同时覆盖：覆盖层与按钮几何重合、04 区块同样可唤起、禁用态不被绕过、页面零未捕获异常。

**工程沉淀**：构建审计新增第 7 条护栏 —— 扫描产出里所有 `type="file"` 标签，**只要出现 `hidden` 就直接构建失败**，并强制必须带 `.shot-file` 覆盖层类。同一个坑不会再犯第二次。

**诚实说明**：本机没有 WebKit / 真机，自动化跑的是 Chromium + iPhone 仿真 + 触摸事件。所以「触摸能唤起选择器」是**实测**结果；而「iOS Safari 拒绝 `display:none` 的 file input」这条属平台已知行为，**仍需在真机上复点一次最终确认**。

**这道题的方法论价值**：①先立「部署/缓存」「元素被遮挡」两条假设把范围收窄，而不是拿到 bug 就改代码；②抓住「桌面好、手机坏」这个分水岭去锁定平台差异；③修复选「让原生路径生效」而非「再补一次程序化 click」；④把教训固化成**构建期护栏**而不是写在文档里等下次忘。同时它也暴露了一个习惯问题：**只在桌面浏览器上测，等于没测移动端**。

## 渠道约束评估：为什么妙回在微信里打不开，以及该怎么办（v0.13 · 2026-10-14）

**背景**：用户实测反馈——在微信里点击分享链接，看到平台引导页「请在浏览器中打开 / 当前应用不支持在微信内打开」。而妙回的使用场景恰恰最集中在聊天里，所以"必须切浏览器"被判断为会显著拉低使用率。

### 结论：不是微信拦我们，是托管平台拦微信；且三重约束叠加后，应用层无解

排查没有靠猜，全部是可复核的实测。方法＝**在同一台机器上只替换 `User-Agent`**（这台机器并不在微信环境里），观测服务器行为差异。

| 探测 | 微信 UA | Chrome UA |
|---|---|---|
| `GET /` | 403 + 3541 字节引导页 | 200（78629 字节） |
| `GET /index.html` | 403 + 引导页 | 200 |
| `GET /manifest.json` | 403 + 引导页 | 404（正常缺文件） |
| `GET /favicon.ico`、`/anything-else` | 403 + 引导页 | 404 |
| 第三方同平台应用 `qm.app.workbuddy.host/` | 403 + 引导页 | 200（130917 字节） |

三条结论由此确定：

1. **锁 1 · 网关按 UA 拦截，与路径无关。** 该域上任何静态路径对微信 UA 都返回同一个 403 引导页（`Cache-Control: no-store`）。第三方同平台应用表现完全一致 → 这是平台策略，不是本应用的问题。
2. **锁 2 · 云接口有严格 Origin 白名单。** 抓包确认线上页面只请求两个域名：`cdn.jsdelivr.net`（字体 + 云 SDK）与 `miaohui-reply.app.workbuddy.host`（接口 `GET /.cloud/llm/models`、`POST /.cloud/llm/chat/completions`）。鉴权头是**公开的** `x-wb-webapp-access-key`（不是 Cookie）。于是直测 CORS：
   - `Origin: https://miaohui-reply.app.workbuddy.host` → **200**，`Access-Control-Allow-Origin` 原样回显该域，`Vary: Origin,X-Wb-Webapp-Access-Key,Authorization`
   - `Origin: https://workbuddy.link` → **403**；`Origin: https://attacker.example.com` → **403**；OPTIONS 预检 → **403**
   - 即：接口**只认自己那个 reserved domain**，从任何别的源都调不通。
3. **锁 3 · 页面必须与接口同源，而那个源在微信里进不去。** 所以"把页面换到微信能打开的域名去托管"这条最直觉的思路，在第二步就会撞墙——页面能开，接口却调不通，"生成回复"直接失效。

**一个重要的中间发现（差点走错方向）**：接口路径 `/.cloud/*` 对微信 UA **不拦截**（微信和 Chrome 都返回 401，而不是引导页）。这曾让人以为"页面换域 + 接口留原地"可行——是第 2 条 CORS 实测把它否掉的。**这说明只测页面不够，必须把接口链路一起测。**

### 顺带否掉的一条网上流传方案

有资料称「WorkBuddy 里放进资料库、再分享为链接（`workbuddy.link/p/xxx`），微信内可正常访问」，并认为 `*.workbuddy.host` 这种随机数字子域被微信判为有风险。这条路对**纯静态页**可能有效，但对妙回无效：

- 页面上任何一次模型调用/登录/同步都要打那个被 Origin 白名单绑死的域 → 撞锁 2；
- 本机对 `workbuddy.link` 的 HTTP 连通性无法验证（沙箱网络不通，仅 DNS 可解析），因此也没有把它当作已证实的方案。

### 可行的方向与取舍

| 方向 | 能不能真正在微信里用 | 代价 |
|---|---|---|
| **A. 加 PWA 能力**（manifest + `apple-touch-icon` + 相关 meta），首次从浏览器打开后「添加到主屏幕」 | 部分：只有"用户自己的第二次及以后"绕过微信入口，**分享给别人仍不行** | 低。要新增图标 PNG 文件随部署上传（iOS 的 `apple-touch-icon` 不支持 data URI），并重新发布 |
| **B. 换成自带 API Key 的直连版本**，摆脱云服务 Origin 绑定，页面改放资料库 | 可能（未经真机验证） | 中。丢掉"免密钥、零门槛"这个最大卖点，且要求用户自备 Key 并付费；前端带 Key 还有泄露风险 |
| **C. 做微信小程序** | 是，微信生态内唯一原生形态 | 高。需小程序主体资质、认证、开发、审核；且当前平台**无法产出小程序**，等于重做一个客户端 |
| **D. 换托管 + 自有备案域名 + 自建后端** | 是 | 高。要重新写后端、自付模型费用 |

### 产品层的判断（这段是真正的产品结论）

**妙回的工作流本身就是跨应用的**：用户在微信收到消息 → 切到妙回 → 生成 → 复制 → 切回微信粘贴。也就是说，"跨应用"本来就是固有成本，微信入口被拦真正影响的是**首次进入**这一步。因此：

- 该优化的是**首次进入的摩擦力**（方向 A：把它装到手机桌面上，此后一步直达），而不是试图把页面塞进微信；
- 同时要接受：**"分享给朋友、让朋友在微信里直接点开就用"这个增长路径，在当前技术形态下走不通**。这是渠道约束，属于产品假设需要修正的部分，而不是工程 bug。

**这段复盘的价值**：这是一个典型且真实的"渠道/平台约束"案例——识别约束 → 用三重独立证据定位（UA 探测、接口抓包、CORS 预检）→ 排除掉最直觉但错误的方案 → 给出四条路径的成本收益取舍 → 修正产品假设。比"我把界面做得好看了"更有说服力。



1. 长度上限：单条默认 ≤ 40 字（若风格样本显示用户习惯长句则放宽）
2. 禁用套话："期待您的回复""收到，谢谢！""非常感谢""我理解您的感受""希望这能帮到你"
3. 禁用词：亲、您（除非样本里用户就用"您"）、"首先/其次/总而言之"、滥用破折号
4. 标点跟随样本：聊天里人经常不打句尾标点、少用分号
5. emoji 与"哈哈/6/草"类语气词：只允许出现在风格样本中出现过的类型
6. 每条候选必须"可直接复制粘贴发送"，不需要用户再改字

## 免费托管方案评估：换托管能不能解决"域名带 workbuddy / 微信打不开"（v0.13 · 2026-10-15）

**背景**：用户收集了一批"免费网站上线方案"（GitHub Pages / Vercel / Netlify / Cloudflare Pages，以及"买独立域名绑定"），希望判断哪些可行。三个诉求必须拆开算：① 链接里别出现 workbuddy；② 微信里能直接打开；③ 功能不能丢。

### 第一步：先盘点资产在哪儿（这是判断"能不能搬"的前提）

| 资产 | 位置 | 说明 |
|---|---|---|
| 页面代码 | 本地 `index.html`（V0.13，80,160 B）+ 平台服务器一份（**V0.12**，78,629 B） | 本地比线上新一版（移动端截图上传修复尚未发布）。代码就是一个 HTML 文件，可整体搬迁 |
| 账号 + 风格档案 | WorkBuddy 云数据库 | 既不在本地，也不在 HTML 里；浏览器只存会话令牌 + 一份本地缓存 |
| 模型调用 | 平台网关 `/.cloud/llm/models`、`/.cloud/llm/chat/completions` | 页面内**没有任何模型 API Key**（免密钥机制）；鉴权用公开的 `x-wb-webapp-access-key` |
| 第三方依赖 | `cdn.jsdelivr.net` | 首屏 23 个请求里 20 个打这里（ZCOOL KuaiLe / Caveat 的 woff2 + 云 SDK）。搬迁时必须自托管，否则字体退化、SDK 加载失败则应用直接不可用 |

**核心结论：能搬走的只有第一行。** 后三行都钉在 `miaohui-reply.app.workbuddy.host` 这个 origin 上。

### 第二步：四条免费方案的实测（用真实浏览器测，2026-10-15 17:08）

测量方法说明：**不能用 `Invoke-WebRequest`/curl 当证据**——本次实测中该通道自身结果自相矛盾（同一个 jsDelivr 两分钟内先 200/430ms、后超时失败）。改用 Node + Edge 真实浏览器逐个访问，与用户真实通道一致。脚本 `scripts/check-host-reach.cjs`。

| 平台 | 默认域名 | 本机实测 | 首次加载 |
|---|---|---|---|
| GitHub Pages | `*.github.io` | 通（跳转 pages.github.com） | 9.6s |
| Netlify | `*.netlify.app` | 通（跳转 netlify.com） | 5.9s |
| Cloudflare Pages | `*.pages.dev` | 通（跳转 cloudflare.com/products/pages） | 12.6s |
| Vercel | `*.vercel.app` | **不通** | DNS 解析到 Facebook 网段（`face:b00c`）= 典型污染，连接超时 |
| （基线）现有线上 | `miaohui-reply.app.workbuddy.host` | 通 | 3.3s，二次 29ms |

注：测的是**平台默认域名的可达性**（根域 404/跳转也算"通"），不等于任意已部署子域的可用性；且可达性随地区/运营商/时间变化，本机数据只作参考。

**但可达性不是决定因素。** 真正卡死的是前文已实测的两条锁：

- **锁 2（Origin 白名单）**：页面搬到任何新域名 → 调接口必然 403，生成 / 登录 / 云同步全部失效；
- **锁 1（微信 UA 拦截）**：新域名在微信里能不能开取决于新域名的信誉，与妙回无关；海外新域名在微信内被拦概率不低。

所以这四条方案**只能替换"页面"这一层**，对"大脑"和"入口"两层零作用。用户资料里"别人反馈打不开就让他复制链接到微信里打开"这条经验，对妙回正好相反（实测微信 UA 返回 403 引导页）。

**顺带修正三处不准确的说法**：① "带数据库项目用 Vercel 免费套餐自带数据库"——Vercel 本身不提供数据库，需外接第三方（Neon / Supabase 等），额度有限且库在海外，国内访问同样不稳；② "海外托管个人静态站不需要 ICP 备案"——备案确实免了，但未备案域名无法走国内 CDN 加速，所以"免备案"与"国内访问稳定"本质是二选一；③ 免费版普遍禁止商用，且默认域名的国内可达性本身不可靠。

### 第三步：那什么才真正可行

| 方案 | 解决哪个诉求 | 为什么可行 / 不可行 |
|---|---|---|
| **PWA：装到手机桌面** | ① 看不到网址 | **唯一能真正让地址栏消失的办法**。二维码解决不了（扫码后地址栏照样显示域名）；"添加到主屏幕"后以 standalone 模式启动，地址栏整个消失，图标写"妙回"。零成本、零域名、零备案。局限：只对用户自己和自己的设备有效 |
| **GitHub 仓库 + Pages** | 干净的代码地址 | 地址 `github.com/<用户名>/miaohui`，干净专业、不含平台名。Pages 上放"演示版"（薄页面：不登录、不依赖平台接口，或用预置样例展示生成效果）。**注意：这是代码展示页，不是可用产品的替代** |
| **B 方案：自带 API Key 直连版** | ①② 都可能 | 唯一能让页面搬到任意域名后"还能生成"的路径（摆脱 Origin 绑定）。代价：丢掉"免密钥、零门槛"，用户自备 Key 并自付费用，前端带 Key 有泄露风险 |
| **C 小程序 / D 自有域名 + 备案 + 自建后端** | ①②③ | 都需要主体资质。C 是微信生态内唯一原生形态；D 只是在网页形态下绕开域名的表面问题 |

**产品结论**：用户的直觉是"换个免费托管就能解决"，但正确的判断是——**诉求①（干净域名）和②（微信入口）在免费方案里无解，因为它们是渠道约束；而①与③（功能不丢）直接冲突。** 最终建议是"用 PWA 让应用以独立形态运行 + 用 GitHub 仓库承载代码展示"，即**不为一个表层诉求去承担主体资质的成本**。

**这段复盘的价值**：这段的价值在于"把三个诉求拆开算"以及"先盘点资产归属再谈搬迁"。多数人会直接比较托管商优劣，而正确的第一步是问一句：**这个应用里，到底是哪一部分需要搬？搬得走吗？** 答案是一层能搬、两层搬不走，于是所有"换托管"方案的结局就注定了。

## PWA：把"地址栏里有别人的域名"这件事从体验里拿掉（v0.14 · 2026-10-15）

**要解决的问题**：分享出去的是 `https://miaohui-reply.app.workbuddy.host/`。对一个想被日常使用的工具来说，这个地址既长、也不属于产品自己。最初的设想是用二维码，但**二维码解决不了这件事**——扫完打开，地址栏里照样是那一串域名。

**关键区分（这是本节的核心判断）**：要区分「**入口形式**」和「**运行形态**」两件事。
- 二维码 / 短链改变的是**入口形式**——用户怎么来到这个页面。地址栏该显示什么还是显示什么。
- 真正能让**地址栏消失**的只有一种：**让页面以独立应用形态运行**。在 Web 上就是 PWA 的 `display: standalone`——「添加到主屏幕」后从桌面图标启动，没有浏览器外壳，没有地址栏，图标名字是自己定的「妙回」。

**做法**（本版只做加法，不动任何一行业务逻辑）：
1. `manifest.webmanifest`：`name / short_name / display: standalone / theme_color / background_color / start_url ./ / scope ./`，声明 192、512 两种图标（512 同时标 `maskable`，供 Android 自适应图标裁剪）；
2. iOS 专属的 `apple-touch-icon`（**必须真 PNG，不支持 data URI / SVG**）+ `apple-mobile-web-app-capable` + `apple-mobile-web-app-title` + `apple-mobile-web-app-status-bar-style`；
3. 图标用项目自己的品牌涂鸦（`pwa/icon.svg`）渲染：Playwright 按 180 / 192 / 512 三种目标尺寸**直接截图**，而不是从大图缩放，避免糊边；
4. 复用原有构建链路：新增 `scripts/shell-v0.14.html` 承载视觉层改动，`scripts/build-shell.cjs` 照旧把视觉层与 V0.10 逻辑层基线机械拼接——所以**功能一个没动**（审计第 6 条"逻辑层字节一致性"仍然通过）。

**一个刻意的"不做"：不加 Service Worker。** 常见的 PWA 教程都会把 SW 一起加上，但 SW 会引入一层缓存，而本项目此前刚吃过"用户打开看到的还是旧版本"的亏（V0.5 缓存问题）。而 iOS「添加到主屏幕」的独立运行**并不需要** SW——它只需要上述 meta 标签。所以这里刻意不引入一个收益很小、却会重新制造版本不一致问题的组件。

**新增两条构建护栏**（`scripts/build-shell.cjs`）：
- [8] 扫描产出里 `manifest` / `apple-touch-icon` / `apple-mobile-web-app-capable` / `apple-mobile-web-app-title` 四项标签，缺一即构建失败；
- [8b] 检查 `manifest.webmanifest` 与 180 / 192 / 512 三个 PNG 图标文件确实存在（防止"标签写了、文件漏传"，那会让 iOS 静默退化成普通书签）。

**验证**：构建审计全绿（当时 10 项：原 6 项 + 移动端 2 项 + PWA 2 项）；桌面功能冒烟 22/22；移动端 17/17；线上抓取与本地**逐字节一致**（80,979 B，版本号 V0.14），`manifest.webmanifest` 与三个图标线上均 HTTP 200，浏览器内能解析出 `display=standalone` 与 3 个图标；线上页面零未捕获异常。证据：`scripts/check-live.cjs` → `docs/evidence/live-report.txt`、`docs/screenshots/`。

**边界（诚实说明）**：
- PWA 只对**用户自己的设备**生效——装到桌面后从此直达、无地址栏；**但对"分享给别人、别人第一次点开"没有帮助**，那一段仍然受渠道约束（见上一节）。
- 本机没有真机，iOS「添加到主屏幕」的最终效果**需在真机上复点一次确认**。Android / 桌面 Chrome 的安装条件由 manifest 满足，可实测。

**这段复盘的价值**：这是一个"**把提出的方案（二维码）换成正确方案（PWA）**"的例子。用户带着一个具体解法来，直接照做能交付、但没解决问题；真正需要的动作是先问"你想解决的问题本质是什么"（地址栏暴露域名）→ 再区分入口形式与运行形态 → 才会落到 PWA。同时"刻意不加 SW"体现的是**知道自己放弃了什么、以及为什么**，而不是照抄教程清单。

## 生成耗时修复：把「默认值」当成一个需要验证的假设（v0.15 · 2026-10-15）

**现象**：真实使用中报「领导发『你好』，选『接住话头』，生成等了**两分钟**」，而另一些场景十来秒就出来了。这个差异很关键——它说明问题出在"每次生成的可变因素"上，而不是"模型整体很慢"。

**定位三步**（每一步都在缩小范围）：

1. **先看代码怎么选模型**：

   ```js
   const models = await cloud.llm.models.list();
   model = models.find(m => m.disabled !== true);   // 取列表里第一个未禁用项
   ```

   这是"能跑就行"的写法：它把**模型选型**这件事交给了平台返回的列表顺序。

2. **再拉真实列表**：32 个模型，**第一位是平台的默认模型 `auto`**（描述是"自动为每个任务匹配最优模型，积分倍率随之浮动"）。也就是说，产品实际上一直在用平台的路由器，而它把任务分派给谁、要算多久，我们既不掌握也控制不了——**"自动"在这里不是优化，是把不确定性引进了最核心的一条路径**。

3. **最后量**（同一条真实 prompt，各模型对照，单次 75 秒上限）：

   | 模型 | 首字 | 全部完成 | 输出 |
   | --- | --- | --- | --- |
   | `auto`（原本在用） | **>75s 无输出** | **>75s** | 0 字 |
   | `deepseek-v4.1-flash` | 0.9s | **1.5s** | 156 字 |
   | `glm-5.3-flash` | 3.1s | 4.2s | 143 字 |
   | `step-5-preview` | 55.5s | 55.6s | 142 字 |
   | `hy4-preview` | 57.0s | 57.6s | 166 字 |

   **关键测量结论：慢是慢在"首字"**（模型想完才吐第一个字），而不是慢在"输出字多"。所以"让模型少写点字"这类优化根本无效——**这一步省下来的是几秒，换模型省下来的是两分钟。**

**改动**（四条，缺一条效果都会打折）：

1. **显式候选链**，不再依赖列表顺序：`deepseek-v4.1-flash → glm-5.3-flash → deepseek-v4-flash → glm-4.6v`，命中不了再退到其它"支持图片"的模型（截图识别复用同一个模型，所以只收支持图片的）。
2. **首字看门狗**：首选 8 秒不吐字就自动换下一个候选（最多试 3 个）。用户不该陪一个抽风的模型等到底。
3. **等待期可见**：流式输出是 JSON、本来要全部收完才能解析，现在边收边把已经写完的候选先显示出来（"已经写好 1 条（我在的，你说）"）；超过 8 秒还会显示当前在用的模型名，便于用户反馈"哪个模型慢"。
4. **把这三条变成护栏**：模型链选择、首字超时换模型、取消、以及"云 SDK 没加载成功"这几种情况，全部写成可复现用例（21 例，用替身 SDK，不消耗额度），并把"不许回退到取第一个未禁用项"写进构建审计——**防止下次改版把这条经验改没了**。

**结果**：真实页面上端到端实测（真实接口）

| 指标 | 改动前 | 改动后 |
| --- | --- | --- |
| 首个候选可见 | 120 秒量级 | **1.6 秒** |
| 3 条全部完成 | 120 秒量级 | **1.9 秒** |
| 截图识别 | 同量级（原本共用同一个模型） | **2.6 秒** |

**这段复盘的价值**：这是一个"**默认值陷阱**"的实例——代码没有 bug、功能也确实"跑通了"，但线上体验是坏的，因为**最慢的那个选项恰好排在列表第一行**，而"取第一个能用的"看起来无懈可击。三个可迁移的动作：

- **性能问题要分层量，不要整体归因**：网络 / 首字 / 输出长度是三件不同的事，只有量过才知道该动哪一层；
- **把"可用"和"好用"当成两个指标**：功能测试全绿不代表用户愿意等它——**等待时长本身就是产品指标**（这个产品的失败模式不是报错，是用户不用了）；
- **凡是交给平台"自动"决定的关键路径，都要用一个数字把它钉住**（这里是首字 8 秒的看门狗），否则它的行为变化会直接变成你的体验故障。

**一个诚实的遗留**：这次是纯性能取舍，没有重跑质量评测。flash 档在"简单意图"上表现正常，但**委婉拒绝 / 砍价这类需要绕的表达还没对照过**。等 50 条测试集的"像人评分"做完，用数据决定是否按意图分流（简单意图走快模型，难的走大模型）——**不能为了速度牺牲"回得漂亮"这个核心**。

## 风格校准设计

用户贴 3–10 条自己平时发的真实消息 → 从中提炼：句长习惯、语气词、emoji 使用、称呼习惯、口头禅 → 生成时作为 few-shot 参考。样本默认只存在浏览器本地（localStorage）；**只有用户主动点「存为档案」并登录后**才会上云（表 `style_archives`，按登录身份行级隔离）。「本次贴的样本」与「存下来的档案」是两个东西：前者永不落库，后者是用户明确要求的长期资产。

## 隐私设计

**始终不变的三条**：聊天内容不留存、聊天截图不落库（仅用于当次识别与提取）、反馈只保存「意图 + 生成的回复 + 评价 + 原因」，不含聊天上下文。

**风格档案分两种状态**：

- 未登录：只存在你自己的浏览器本地，不上传
- 已登录：你**主动保存**的档案同步到云端，用于跨设备使用。除此之外没有任何数据上传

**可见性由数据库保证**：云端档案表按登录身份做行级隔离，任何人都只能读写属于自己的行；未登录时该表对它完全不可见（读 0 行、写被拒，已实测）。页面上明示隐私说明，登录弹层内也再次说明"同步的只有你主动保存的风格档案"。

## 成功指标（评测口径）

- 量化指标：50 条真实对话测试集上的"像人评分"（1–5 分，由真实用户盲评）
- 北极星：**用户采纳率**——生成后直接复制发送的比例
